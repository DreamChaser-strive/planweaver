# PlanWeaver 客户端验收清单

> 用途：在 WorkBuddy 客户端安装 Skill 后，逐条复制执行，判断是否达到发布标准。
> 状态：**待人工验收**。本清单由我编写，但我无法操作客户端 GUI，因此**没有任何一条被标记为"已通过"**。
> 每条都给出"不通过时查什么"——指向具体文件或机制，便于定位是提示词问题还是代码问题。

## 0. 环境准备（2 分钟）

1. 安装：技能市场 →「添加技能」→ 导入 `dist/planweaver-1.0.0.zip`
2. 确认列表中出现 **PlanWeaver 全域智能规划师** v1.0.0
3. 新建对话，先发一句触发词测试：`帮我规划一下接下来三个月`

**若安装即失败**：先看 `release/RELEASE-CHECKLIST.md` §7，再换 `dist/planweaver-1.0.0-flat.zip` 重试（两者内容相同，只是 ZIP 层级不同）。

## 1. 三领域统一规划（学习 + 工作 + 生活）

**复制这条：**

```
帮我规划一下：三个月内把雅思考到 6.5，手上有个项目 11 月中要交付，还想每周运动三次。
我每周大概能挤出 15 小时，晚上 8 点后基本没精力。
```

**预期行为**

- 先把三个目标放进**同一份**时间账本，算出"有效可用 vs 需求"的具体数字（不是三份独立计划）
- 给出可行 / 紧张 / 不可行三档判定之一，并说明依据
- 给出保底 / 标准 / 冲刺三方案对比，差异在**范围与验收标准**上
- 明确"放弃什么"和"什么不换"（睡眠、休息）
- 近期清单 ≤ 2 周，按优先级排序

**验收标准（全部满足才算通过）**

| # | 检查点 | 通过条件 |
|---|---|---|
| 1.1 | 有统一账本 | 出现"有效可用 = 周可用 × (1 − 缓冲)"这类算式，且**只有一份**总容量 |
| 1.2 | 有判定 | 明确写出可行/紧张/不可行，不是含糊的"应该可以" |
| 1.3 | 三方案有实质差异 | 三栏对比里范围/验收标准不同；不是"每天 2h / 3h / 4h" |
| 1.4 | 有取舍 | 明确指出放弃了什么（如"雅思写作单项 6.5"） |
| 1.5 | 不牺牲休息 | 没有把睡眠/运动时间拿去填任务 |

**不通过时查**

- 没有算式 / 三份计划 → `planweaver/SKILL.md` §5.1、`references/planning-framework.md` §1.3–1.4
- 三方案只改数量 → `references/planning-framework.md` §6.1
- 数字对不上 → 用 `scripts/validate_plan.py --format text` 复核 metrics

## 2. 时间预算不足时的目标取舍

**复制这条：**

```
我每天只有 2 小时，但想在 4 周内学完三门课并且都通过考试。帮我排。
```

**预期行为**

- 直接算出缺口（需求 vs 容量），**明确说不可行**
- 给出四类出路中的至少三类：缩小范围 / 延长周期 / 增加资源 / 调整优先级
- 不出现"提高效率""挤一挤""加把劲"这类空方案
- 不把睡眠时间算进可用时间

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 2.1 | 敢说不行 | 出现明确的"不可行/做不到"，而不是勉强排出来 |
| 2.2 | 有缺口数字 | 给出需求分钟数、可用分钟数、缺口 |
| 2.3 | 四类出路 | 至少三类具体选项，且说明各自代价 |
| 2.4 | 无空话 | 全文不出现"提高效率/挤一挤/更自律"作为解决方案 |

**不通过时查**

- 硬排出来了 → `SKILL.md` 红线 R2、`references/planning-framework.md` §1.5
- 有数字但没出路 → 同上 §1.5 表格
- 校验器层面 → `validate_plan.py` 的 `E_CAPACITY` / `E_DEADLINE_INFEASIBLE`

## 3. 新增紧急任务后的变化影响分析

**复制这条（先做第 1 条建立计划，再发这条）：**

```
客户临时要求下周三前加一份渠道拆分说明，大概要 4 小时。帮我看下影响。
```

**预期行为**

- 先问清或推断：这 4 小时从哪一周的池子里出（而不是凭空多出 4 小时）
- 指出**被挤占的目标**与**哪个里程碑会失守**
- 给出调整方案（重排/降级/加时），并说明代价
- 若空间不足，明确说"这周已经没有余量"

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 3.1 | 有占用来源 | 明确指出从哪一周/哪个任务挪时间 |
| 3.2 | 有被影响方 | 点名受影响的目标或里程碑（不是"会影响进度"） |
| 3.3 | 有方案 + 代价 | 至少一个可执行调整，且写明代价 |
| 3.4 | 没凭空扩容 | 没有把周可用时间悄悄改大 |

**不通过时查**

- 只说"会更忙" → `references/replanning-playbook.md` §2（`new_work` 类型）、§3.1
- 影响域算错 → §3.2 的闭包示例
- 记录侧 → `plan_tool.py replan --trigger-type new_work`

## 4. 关键任务延期后的动态重规划

**复制这条：**

```
项目评审被客户推到下周三了，我后面写报告和做汇报材料的活全卡住了。原定 11/20 交付。
```

**预期行为**

- 区分**直接受影响**（等评审的任务）与**间接受影响**（依赖它们的下游）
- 先算余量：余量够就 S0 吸收（不改排期），不够才 S1 重排
- 说明原截止是否仍成立；不成立就报不成立
- 不把整张表一起后移

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 4.1 | 影响分两层 | 分别列出"直接受影响"和"依赖它的下游" |
| 4.2 | 先算余量 | 出现余量判断（如"还剩 3.1 天，够吸收 3 天延迟"） |
| 4.3 | 策略有依据 | 说明为什么用 S0/S1，以及为什么没跳到 S2/S3 |
| 4.4 | 截止判断明确 | 明确"仍可行"或"不可行"，并给数字 |

**不通过时查**

- 全量顺延 → `SKILL.md` 红线 R3、`references/replanning-playbook.md` §1
- 没算余量 → playbook §3.3
- 跳级压缩 → playbook §4（S2 上限 15%，且不碰休息）
- 工具层 → `validate_plan.py` 的 `W_ROLLOVER` / `W_ROLLOVER_MASS`

## 5. 不受影响的任务是否得到保留

**与第 4 条同一次对话里继续问：**

```
那哪些安排是不用动的？
```

**预期行为**

- **明确列出**保持不变的任务（名称或编号），并说明"这些按原排期"
- 不是笼统说"其他不变"，而是点名

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 5.1 | 有"不变清单" | 至少列出 2 个具体任务名/编号 |
| 5.2 | 前后一致 | 第 4 条说移动的任务，与这里说不变的任务不重叠 |
| 5.3 | 不偷偷改动 | 若后续再问一次，答案应稳定（不自相矛盾） |

**不通过时查**

- 只给"其他不变" → `SKILL.md` §6.2 第 3 段（"哪些任务保持不变"是必填段）
- 前后矛盾 → `references/replanning-playbook.md` §5 第 10 步（记录变更）
- 状态层 → `plan_tool.py replan` 写入的 `moved_task_ids` 应只含真正移动的任务

## 6. 跨会话的计划状态读取与更新

**第一步 · 建一份真实状态文件（在本地终端执行，不是对话里）**

```bash
cd planweaver
python scripts/plan_tool.py init --out ./my-plan --horizon-start 2026-10-19 --weeks 8 --weekly-minutes 900 --title "验收测试计划"
```

**第二步 · 在新对话里复制这条（把路径换成你的真实路径）：**

```
这是我上次的计划，帮我接着排：./my-plan/plan-state.json
另外 T1 已经做完了，实际花了 150 分钟（预估 120）。
```

**预期行为**

- 读取该文件并复述关键信息（目标、周可用、当前判定），而不是假装读过
- 更新 T1 状态为完成、记录实际耗时 150
- 指出实际比预估多 25%，并判断是否影响后续
- 明确说明是否已写回文件

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 6.1 | 真读了 | 复述的内容与文件一致（可用 `summary` 核对） |
| 6.2 | 更新了状态 | 文件里 T1 的 `status` 变 `done`、`actual_minutes` = 150 |
| 6.3 | 有偏差判断 | 指出 150 vs 120 的偏差及其影响 |
| 6.4 | 不谎报保存 | 若环境不能写文件，必须明说"未保存"，而不是说"已更新" |

**核对命令**

```bash
python scripts/plan_tool.py summary --state ./my-plan/plan-state.json
```

**不通过时查**

- 复述错 → `references/state-schema.md`（字段含义）、`plan_tool.py summary`
- 没写回 → `plan_tool.py update --task T1 --status done --actual 150`
- 假装读过 → `SKILL.md` 红线 R1、§7 "用户没给旧状态时不得假装读过"

## 7. 不可行目标的风险提示

**复制这条：**

```
我想两个月内从零基础达到能接商业项目的水平，同时还在全职上班。你觉得行吗？
```

**预期行为**

- 明确说"以现有条件不可行"，并说明缺什么
- 给出"什么条件下才可行"（每天几小时 / 延长到多久 / 降低什么标准）
- **不承诺**"你一定能做到"
- 不贬低用户（不说"你不自律"）

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 7.1 | 明确否定 | 出现"不可行/不现实"，而非"可以试试看" |
| 7.2 | 给出条件 | 说明需要多少时间/多长时间才可行 |
| 7.3 | 不承诺结果 | 全文无"保证/一定能/肯定可以" |
| 7.4 | 不评判人 | 无"你不够自律/你拖延"类表述 |

**不通过时查**

- 说"可以试试" → `SKILL.md` 红线 R4、`references/planning-framework.md` §1.5
- 出现承诺 → `SKILL.md` §9 自检清单第 9 项
- 归因到人 → `references/calibration.md` §3 归因顺序

## 8. 用户修改优先级后的方案调整

**复制这条：**

```
项目比考证重要，先把项目保下来，考证可以往后放。帮我重排。
```

**预期行为**

- 识别这是 `priority_change`，重排资源分配
- 说明考证会被推迟到什么程度、哪些验收标准会失守
- 更新后的计划仍满足容量约束（不是简单把考证任务删掉）
- 明确记录"用户已确认优先级变更"

**验收标准**

| # | 检查点 | 通过条件 |
|---|---|---|
| 8.1 | 类型识别 | 按优先级变更处理，不是当成"取消目标" |
| 8.2 | 有代价说明 | 说明考证被推迟多久、失去什么 |
| 8.3 | 容量仍成立 | 重排后没有超载（可让 Skill 跑校验或自己核对） |
| 8.4 | 有确认 | 涉及放弃/降级时，明确说"需要你确认" |

**不通过时查**

- 直接删任务 → `references/replanning-playbook.md` §2（`priority_change`）、§4（S1 不动范围）
- 没算代价 → 同上 §7.2 取舍对比表
- 记录侧 → `plan_tool.py replan --trigger-type priority_change --strategy S1`
