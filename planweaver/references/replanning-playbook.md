# 重规划手册：变化分类、影响域与策略阶梯

本文件是模式 E（动态重规划）的执行细则，也是本 Skill 与普通"待办清单工具"的核心差异。

**一句话原则：变化只应该改变它真正触及的部分；把整张计划推倒重排，是把用户的确定性当消耗品。**

---

## 1. 为什么禁止"全量顺延"

用户说"我落后了三天"，最省事的做法是把所有未完成任务整体后移三天。这有三个致命问题：

1. **错误的因果**：落后三天往往只影响一条链，其余任务的原排期仍然成立。全量后移制造了本不存在的延期。
2. **截止日期失真**：所有任务同时后移，硬截止会被无声突破。
3. **心理成本**：用户看到整张表变了，会认为"计划已经废了"，从而放弃。

正确做法：算出受影响集，只动它，其余冻结并明确告知"这些不变"。

---

## 2. 变化分类

收到变化后，先归类，再决定流程。类型判断错，后面全错。

| 类型 | 典型表述 | 关键判断 | 默认起始策略 |
|---|---|---|---|
| `delay` 进度落后 | "落后三天""这周没做完" | 落后的是哪条链？有无余量？ | S0 |
| `new_work` 新增任务 | "下周多个项目""临时加急" | 它抢哪一周的池子？有硬截止吗？ | S0 → S2 |
| `deadline_change` 截止变化 | "提前一周""延后一个月" | 硬性还是软性？谁改的？ | 提前 → S2/S3；延后 → S1 |
| `resource_change` 资源变化 | "下周出差""生病了""预算砍了" | 减多少？持续多久？ | S3 |
| `scope_change` 范围变化 | "要求变了""多做一版" | 新增工作量？验收标准变了吗？ | S2/S3 |
| `priority_change` 优先级变化 | "这个先放放""那个更重要" | 新优先级与依赖是否冲突？ | S1 |
| `abandon` 放弃目标 | "不想考了""项目取消了" | 释放多少资源？谁依赖它？ | S5（用户拍板） |
| `early_completion` 提前完成 | "我做完了""比预想快" | 省下的时间给谁？ | S1（回填） |

**多类型混合**（"项目延后了，但下周又加了新活"）：分别计算影响域，取并集，再统一排。不要只处理一个。

## 3. 影响域计算（必须按图算，不许凭感觉）

### 3.1 四类影响

```
直接受影响 = 变化直接命中的任务集合 D
间接受影响 = D 的下游闭包（依赖 D 中任一任务的任务，递归）∪ D
资源受影响 = 与 (D ∪ 下游) 争同一周时间池、且该周已无余量的任务
里程碑影响 = 含 (D ∪ 下游) 任务的里程碑
```

**冻结集 = 全部任务 − (直接 ∪ 间接 ∪ 资源受影响)**

冻结集必须在输出中列出。这是对用户的承诺：这些安排不会变。

### 3.2 手算示例

任务图（→ 表示依赖）：

```
T1 → T2 → T3 → T6
T4 → T5 → T6
T7（独立）
```

用户报告 T2 延期 2 天：

- 直接：`{T2}`
- 间接（下游闭包）：`{T3, T6}`
- 受影响：`{T2, T3, T6}`
- 冻结：`{T1, T4, T5, T7}` ← **T1 已完成或不受影响，T4/T5 是另一条链，T7 独立**

正确输出：只重排 T2/T3/T6，并明确说 T4、T5、T7 不变。

错误输出：把 T3–T7 全部后移两天。

### 3.3 余量（slack）检查

对直接受影响的任务，检查其下游链的余量：

```
链余量 = min(下游各任务 due − 预计完成时间)
```

- 链余量 ≥ 延迟量 → 用 S0 吸收，**排期完全不用改**，只更新进度
- 链余量 < 延迟量 → 差额 = 延迟量 − 链余量，进入 S1

**很多"落后"根本不需要改计划**，只需要更新状态。先算这一步，能省掉大量无谓重排。

### 3.4 硬截止与软截止

| 截止类型 | 允许的操作 |
|---|---|
| 硬性 | 不可延；只能 S0–S3；若 S3 仍不可行 → 报"该目标在现有资源下不可达"，给 S5 |
| 软性 | 可延（S4），但必须用户确认新日期 |
| 开放 | 先补日期，再判断 |

**禁止**：为了"让计划看起来成立"，把硬截止当软截止悄悄改掉。校验脚本会对"硬截止累计负荷超容量"直接报错。

## 4. 策略阶梯

按顺序尝试，**能停在前面就不许跳到后面**。每次重规划必须在记录里写明试过哪些、为什么放弃。

### S0 · 吸收（Absorb）

- **做什么**：不动排期，用现有缓冲/余量吸收延迟。
- **前置**：链余量 ≥ 延迟量。
- **输出**：更新进度 + 说明"排期不变，余量从 X 降到 Y"。
- **代价**：后续容错空间变小。必须提示。

### S1 · 重排（Reorder）

- **做什么**：在**同一周内**调整任务顺序，把被阻塞的任务与可并行的任务换位。
- **前置**：不破依赖、不破截止、不引入新的资源冲突。
- **上限**：不动任务范围、不动验收标准、不跨周挪动硬截止链。
- **输出**：给出换序前后的对比（哪天做什么变了）。

### S2 · 压缩（Compress）

- **做什么**：缩短任务时长，提高单位时间投入。
- **前置**：任务标记 `compression_safe = true`（机械性、可批处理、无质量硬要求）。
- **上限**：
  - 单任务压缩 ≤ 15%
  - 全计划总压缩 ≤ 剩余工时的 10%
  - **绝对禁止**压缩睡眠、用餐、受保护恢复时间
  - 不得假设效率从 70% 提到 100%
- **输出**：明确说"这 15% 是压缩，不是原估算错了"。

### S3 · 降级（Downgrade to 保底）

- **做什么**：切换到保底方案，砍掉非核心成果。
- **前置**：S0–S2 都不足以恢复可行性。
- **必须写明**：砍掉哪条验收标准、哪个里程碑取消、用户会失去什么。
- **禁止**：悄悄降低标准而不告知。

### S4 · 延长期限（Extend）

- **做什么**：把软性截止后移。
- **前置**：截止为软性，或用户明确授权。
- **必须**：给新日期 + 说明对后续目标的影响（是否撞车）。
- **硬性截止不可用此级。**

### S5 · 增资源 / 放弃（Escalate）

- **做什么**：加时间/加钱/找人，或放弃/暂停某个目标。
- **前置**：S0–S4 均不成立。
- **纪律**：这是用户的人生决策，**必须由用户拍板**；你只给可比较的选项和后果。

## 5. 十步流程（照做，不要跳）

```
1. 读状态        读 plan-state.json；没有就问用户要，不许假装读过
2. 确认变化      用一句话复述事实，让用户确认（"T2 延期 2 天，其他不变，对吗"）
3. 算影响域      §3.1 四类影响 + 冻结集
4. 分受影响/不受影响   列出两个清单
5. 判断可行性    链余量？硬截止还成立？整体判定是否降级？
6. 生成方案      至少 2 个可比较方案（不同策略级）
7. 说明代价      每个方案的代价、风险、放弃的东西
8. 给推荐        按用户已授权偏好推荐一个，说明理由
9. 只更新受影响部分   其余原样保留
10. 记录变更     追加 change-log + replans 记录（含原因、策略、被移动任务）
```

**第 8 步的"已授权偏好"**：用户之前说过的偏好（"宁可延期也不要降标准"/"考试必须过，其他可以放"）算授权；没说过就不要假装知道，直接问或给中性推荐。

## 6. 重规划输出模板（L2 七段）

```markdown
## 变化
[事实] 项目评审延后 3 天（原 11/05 → 11/08）。

## 受影响
- 直接：T3 数据清洗（被评审阻塞）、T5 报告初稿
- 间接：T7 汇报材料（依赖 T5）
- 受影响合计 3 个任务 / 1 个里程碑（M2 初稿完成）

## 保持不变（承诺）
T1、T2 已完成；T4 用户访谈、T6 附录整理、T8 英语听力 按原排期不变。

## 原目标是否仍可行
[估算] 硬截止 11/20 仍可行，但余量从 4 天降到 1 天 → 判定由"可行"降为"紧张"。

## 推荐方案
S1 重排：把 T6 提前到 11/06–11/07 填补等待期，T5 顺延到 11/08–11/10。
代价：T6 提前意味着附录资料要在 11/06 前拿到（需你今天确认资料是否齐）。
风险：若评审再延 2 天以上，将触发 S3 降级（砍掉附录 B）。

## 需要你确认
1. 附录资料 11/06 前能拿到吗？（默认按能拿到处理）
2. 若评审继续延，接受"砍掉附录 B"还是"延后硬截止"？后者不可行，所以实际只有前者。

## 下一步
1. 今天：确认附录资料到位时间
2. 11/06–11/07：整理 T6
3. 11/08：开始 T5 初稿
```

## 7. 多目标冲突（模式 F）

### 7.1 冲突判定

同一资源池 + 时间重叠 + 合计超容量 = 真冲突。

- 时间不重叠（一个上午一个晚上）→ 不是冲突，是排期问题
- 合计未超容量 → 不是冲突，是排序问题
- **真冲突才需要取舍**，不要把所有"两个都想做"都升级成人生抉择

### 7.2 取舍对比表

| 分配方式 | A 得到 | B 得到 | 总风险 | 可逆性 |
|---|---|---|---|---|
| 全给 A | 标准完成 | 延期/放弃 | B 截止失守 | 中 |
| 6:4 | 保底 | 保底 | 双线都不达标 | 高 |
| 分阶段 | A 完整 → B 启动 | B 延后 | B 前期空转 | 低 |

### 7.3 纪律

- 给 2–3 个可选分配，不替你决定
- 说明每个选项"失去什么"，而不只是"得到什么"
- 不评判用户的价值观（"你应该更重视家庭"——越界）
- 用户选定后，把选择写进 `change-log.md`，作为后续重规划的授权依据

## 8. 常见错误（逐条自查）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 全量顺延 | 制造假延期，破硬截止 | 算下游闭包，冻结其余 |
| 只改截止不改任务 | 计划表面成立，实际不可能 | 改截止必须重算容量 |
| 悄悄降标准 | 用户以为还在按原目标走 | S3 必须显式列出砍掉什么 |
| 压缩睡眠凑数 | 短期可行，长期崩盘 | 受保护时段不可动 |
| 假设 100% 效率 | 计划第一天就失效 | 用 (1−buffer) 且按 M 值排 |
| 重规划后不记录 | 下次无法解释为什么改了 | 追加 replans + change-log |
| 一次给 5 个方案 | 用户决策瘫痪 | 最多 3 个，推荐 1 个 |
| 把"落后"等同于"不自律" | 归因错误，方案无效 | 按 calibration.md 的归因顺序查 |
