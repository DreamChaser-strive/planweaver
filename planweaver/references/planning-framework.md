# 规划框架：资源、优先级、估算与容量

本文件是模式 A（全面规划）、C（每日安排）、F（目标冲突协调）的执行细则。所有公式都可以被用户手算复核——不要引入用户看不懂的模型。

---

## 1. 资源账本

### 1.1 为什么要一本账

学习、工作、生活争夺的是同一份时间。分域排期再叠加，必然产出三份都"看起来合理"、合起来不可能执行的计划。这是普通规划工具最常见的失败模式。

**强制规则**：先汇总需求，再分配；禁止先给每个域排一份完整计划。

### 1.2 账本字段

| 项 | 含义 | 取值方式 |
|---|---|---|
| `weekly_minutes` | 每周真正可投入任务的时间（不含固定安排、不含睡眠） | 问用户，或从其作息推算并标注 `[假设]` |
| `fixed_events` | 不可移动的固定安排 | 用户提供；默认全部视为刚性 |
| `protected_blocks` | 必须保留的休息/家庭/运动时间 | 默认每天 ≥ 60 分钟恢复时间 |
| `buffer_ratio` | 缓冲比例，吸收估算误差与突发 | 默认 0.15；估算历史偏差大时提到 0.20–0.25 |
| `energy_pattern` | 高/中/低精力时段 | 影响任务放置，不影响总量 |
| `budget` | 金钱预算（课程、资料、外包） | 仅当用户提出预算约束时启用 |

### 1.3 有效容量

```
有效可用 = weekly_minutes × (1 − buffer_ratio) × 周期周数
需求     = Σ 未完成任务工时（用"通常"估算）
需求上限 = Σ 未完成任务工时（用"保守"估算）
占用率   = 需求 ÷ 有效可用
```

**为什么乘 (1 − buffer)**：估算系统性偏乐观（见 §4）。不留缓冲的计划在第一次意外时就会崩，然后触发"全量顺延"——那正是本 Skill 要避免的。

### 1.4 三层可行性判定

| 判定 | 条件 | 承诺口径 |
|---|---|---|
| 可行 | 保守估算总量 ≤ 有效可用 | 可承诺标准方案 |
| 紧张 | 通常估算 ≤ 有效可用 < 保守估算 | 只承诺保底方案；标准方案加检查点 |
| 不可行 | 通常估算 > 有效可用 | 必须报不可行，给四类出路 |

**承诺用保守值，排期用通常值**——这条纪律同时避免了"过度乐观"和"过度保守导致计划失去意义"。

### 1.5 资源不足时的四类出路

不许说"加把劲"。只给这四类，并说明各自的代价：

| 出路 | 做法 | 代价 |
|---|---|---|
| 缩小范围 | 砍到保底方案的核心成果 | 放弃部分验收标准 |
| 延长周期 | 把软性截止往后推 | 后续目标顺延，可能与下一件事撞车 |
| 增加资源 | 加时间/加钱/找人帮忙 | 需要真实可获得的资源，不能假设 |
| 调优先级 | 明确放弃或暂停某个目标 | 沉没成本，需要用户认账 |

**如果四条都不可接受**，唯一诚实的结论是"当前条件下这个目标不可达"，并说清需要什么条件才可达。

### 1.6 新增目标的影响分析（强制四问）

1. 它要占用多少时间？从哪一周的哪个池子里出？
2. 被挤占的目标，哪个里程碑会失守？
3. 有没有可以先降级（保底化）的任务？
4. 加入后整体判定从"可行"降到"紧张/不可行"了吗？

答不出第 1 问，就不要给方案。

## 2. 优先级：有序比较，不做伪精确打分

### 2.1 比较维度（按字典序）

不要算加权总分——权重是编的，结论会被伪精确掩盖。用字典序依次比较：

1. **截止刚性**：硬性 > 软性 > 开放
2. **用户指定权重**：1–5（用户给，你不替他给）
3. **下游影响面**：被它阻塞的后续任务数（依赖图出度闭包大小）
4. **延迟代价可逆性**：不可逆 > 代价高 > 可逆
5. **已投入量**：仅在其余维度打平时参考（沉没成本不能主导决策）

### 2.2 排序冲突时的处理

- 硬截止 + 低权重 vs 软截止 + 高权重：**先硬截止**，但要告知用户"这会推迟高权重目标"，让他确认。
- 两个硬截止撞车：这是资源不足，不是排序问题 → 走 §1.5。
- 用户权重与依赖关系冲突（低权重任务是高权重任务的前置）：**前置优先**，因为它是通路。

### 2.3 冲突协调输出（模式 F）

当多个目标争同一份资源，输出对比表而不是替你决定：

| 分配方式 | 得到什么 | 失去什么 | 风险 |
|---|---|---|---|
| 全部给 A | A 按标准完成 | B 延期 N 周 | B 的截止可能失守 |
| 6:4 分配 | A 保底 + B 保底 | 两个都不达标 | 双线并行，切换成本高 |
| 先 A 后 B | A 完整，B 延后启动 | B 前期无进展 | B 若为硬截止则不可行 |

必须明确一句：**"这是取舍，不是最优解；选择权在你。"**

## 3. 目标编译

### 3.1 模糊词 → 可验收目标

| 用户说 | 必须澄清的 | 编译后 |
|---|---|---|
| 提高英语 | 用途（考试/工作/口语）、当前水平、期限 | "12 周内雅思写作从 5.5 到 6.5，每周 6 小时，以 4 篇批改作文为验收" |
| 学编程 | 目标产出（能做项目/能面试/能做数据分析） | "10 周完成 3 个可运行项目，覆盖 CRUD + 部署" |
| 减肥 | 指标、基线、期限、可接受方式 | "16 周减 6kg，每周 3 次运动，以体重与腰围双指标验收" |
| 提升工作效率 | 具体瓶颈（拖延/切换/会议） | 先诊断瓶颈，再定目标——不要直接给时间管理法 |

### 3.2 完成标准写法

必须满足三条：**可观察、有阈值、有验证方式**。

- ✗ "掌握 Python 基础"
- ✓ "能独立写出含文件读写与异常处理的脚本，通过 5 道练习题的 4 道"

### 3.3 期限刚性

| 类型 | 例子 | 可动性 |
|---|---|---|
| 硬性 | 考试日、合同交付、签证截止 | 不可动；不可行就报不可行 |
| 软性 | 自定"三个月内" | 可协商，但需用户确认新日期 |
| 开放 | "有空就学" | 必须先补目标日期才能排期；否则只能给"下一步"，不能给路线图 |

### 3.4 前置条件

容易漏的：报名/资格、设备/资料、他人配合（导师、审批、队友）、身体状态、资金到位。前置未满足的任务不能进近期清单——只能进"待解锁"。

## 4. 估算

### 4.1 三点估算

每个非平凡任务给三值：`optimistic`（顺利）、`likely`（通常）、`pessimistic`（不顺）。

```
期望值 E = (O + 4M + P) / 6
```

- **排期用 M**（否则计划过于保守，失去指导意义）
- **承诺用 P**（对外承诺、硬截止判断）
- **E 用于资源总量估算**（更接近长期平均）

三值必须满足 `O ≤ M ≤ P`，否则数据无效（校验脚本会报错）。

### 4.2 颗粒度

- 单任务 **30 分钟 – 4 小时**。超过 4 小时必须拆（"写报告"→ 列大纲 / 找资料 / 写初稿 / 改一遍）。
- 小于 15 分钟的任务合并成批次，否则计划会被琐事淹没。
- 一个阶段内活跃任务 **≤ 12 个**；超过说明拆得太细或目标太多，先合并。

### 4.3 估算不确定性的表达

- 有历史数据 → 用偏差系数 k 调整（见 calibration.md）
- 无历史数据 → 明确说"首次估算，误差可能 ±50%"，并在第一周后校准
- 完全无法估算的任务（探索性、依赖外部）→ 给**时间盒**（"最多投入 4 小时，到点评估"），不给完成承诺

### 4.4 禁止

- 用"高效状态下的耗时"当估算
- 把多个任务的估算按 0.8 打折来"腾出空间"
- 对用户没做过的任务给出精确到 10 分钟的估算

## 5. 容量模型与排期

### 5.1 周容量分配

```
第 w 周可排 = weekly_minutes × (1 − buffer_ratio) − 该周固定安排耗时
```

固定安排耗时从 `weekly_minutes` 里已经排除（用户报的是"可投入任务的时间"），所以不要重复扣减。若用户报的是"总清醒时间"，则必须先扣固定安排再乘缓冲——**问清楚用户报的是哪种口径**。

### 5.2 排期顺序

1. 放固定安排（不可动）
2. 放受保护时段（睡眠、用餐、恢复）
3. 按优先级放硬截止任务的关键链
4. 放其余任务
5. 检查每周占用率；> 85% 的周标记为"高风险周"

### 5.3 每日安排（模式 C）

- 只排**当天真正能做完**的量：`当日可用 × 0.8`，留 20% 给意外
- 任务不必切到分钟；给时间块（上午/下午/晚上）+ 预估时长即可
- 高低精力匹配：深度任务放高精力段，机械任务放低精力段
- 至少保留一段无任务时间；不排满
- 输出：3–6 项，按执行顺序，标注依赖与预计时长

### 5.4 缓冲的三种用法

| 类型 | 位置 | 比例 |
|---|---|---|
| 任务缓冲 | 每个任务估算内 | 已含在 P 值里 |
| 周缓冲 | 每周留白 | 15%（`buffer_ratio`） |
| 项目缓冲 | 里程碑前 | 该阶段工时的 10% |

缓冲不是"可以拿去塞任务的空间"——用了就要在下一轮重算可行性。

## 6. 三方案设计

### 6.1 差异必须落在范围与标准上

| 维度 | 保底 | 标准 | 冲刺 |
|---|---|---|---|
| 目标范围 | 只留核心成果（1–2 个） | 完整目标 | 完整 + 1 个进阶成果 |
| 验收标准 | 最低可接受 | 正常标准 | 提高阈值或加质量要求 |
| 任务集 | 核心链 + 必要前置 | 核心链 + 支撑任务 | 标准 + 拓展任务 |
| 缓冲 | 20% | 15% | 10%（且必须有额外资源） |
| 风险 | 低 | 中 | 高 |

### 6.2 保底方案要真的敢删

判断标准：保底方案的任务量应显著少于标准方案（通常 50–65%）。如果只少 10%，那只是"标准方案的紧凑版"，不是保底。

删除顺序：拓展任务 → 加分项 → 非核心章节 → 降低验收阈值。**核心前置不能删**（删了目标就不成立）。

### 6.3 冲刺方案的门槛

只有满足以下**至少一条**才提供冲刺方案，否则不给（避免制造焦虑）：

- 用户明确说有多余时间/预算/帮手
- 距离截止还有充裕余量（占用率 < 60%）
- 有可复用的既有成果（不用从零开始）

### 6.4 方案对比表（模式 A 必出）

```
| | 保底 | 标准 | 冲刺 |
| 预期成果 | ... | ... | ... |
| 所需资源 | ... | ... | ... |
| 关键里程碑 | ... | ... | ... |
| 适用条件 | ... | ... | ... |
| 主要风险 | ... | ... | ... |
| 取舍 | ... | ... | ... |
```

## 7. 常见失败模式（自查）

| 失败模式 | 表现 | 修正 |
|---|---|---|
| 三份计划叠加 | 学习/工作/生活各一份，合起来 40 小时/周 | 先汇总再分配 |
| 缓冲被吃掉 | 每周排满，第一次意外就崩 | 保留 15%，且不许挪用 |
| 假保底 | 保底方案只比标准少一点 | 按 §6.2 删到 50–65% |
| 估算幻觉 | 没做过的任务给出精确耗时 | 用时间盒 + 区间 |
| 任务过大 | "做项目"当一个任务 | 拆到 ≤ 4 小时 |
| 前置缺失 | 排了任务但资格/资料没到位 | 建"待解锁"清单 |
| 无限细化 | 排到每天每分钟 | 到"周 + 时间块"即止 |
