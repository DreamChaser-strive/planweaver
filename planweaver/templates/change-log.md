# 计划变更记录

> 只记重要变更：影响排期、范围、验收标准、优先级、资源约束的动作。
> 每次记录必须写清「为什么改」，否则三个月后无法解释这份计划。

格式：每条包含 时间 / 类型 / 事实 / 影响 / 策略 / 被移动的任务 / 未受影响的任务 / 用户确认

## 2026-10-22 · 进度更新（不改排期）

- **类型**：`delay`（局部）
- **事实**：T1 数据清洗实际 150 分钟（预估 120），10-22 完成。
- **影响**：仅 T1 本身；T2 排期 10-26 不变。
- **策略**：`S0` 吸收（本周余量 3 天，足够）。
- **被移动的任务**：无
- **未受影响的任务**：T2、T3（排期不变）
- **代价**：本周缓冲从 3 天降到 2.4 天。
- **用户确认**：是
- **校准记录**：数据类任务 k = 150/120 = 1.25（样本 1，仅记录趋势，不启用系数）

## 2026-11-06 · 硬截止冲突（升级决策）

- **类型**：`deadline_change`
- **事实**：管理层把报告提交日从 11-15 提前到 11-10。
- **影响**：硬截止提前 5 天；剩余工作量 6 小时，可用容量 4.5 小时 → **缺口 1.5 小时**。
- **判定**：原标准方案不可行。
- **可选方案**：
  1. `S3` 降级到保底：只做 1 个核心指标 → 可 11-10 交付
  2. `S5` 增资源：请同事协助数据核对（约 1.5 小时）→ 可保住三指标
- **用户选择**：方案 2（同事协助）
- **策略**：`S5`
- **被移动的任务**：无（靠增资源解决，未改排期）
- **未受影响的任务**：全部
- **代价**：引入协作成本与沟通时间；需今天发出请求。
- **用户确认**：是

## 记录规范

| 字段 | 要求 |
|---|---|
| 类型 | 必须是 `delay` / `new_work` / `deadline_change` / `resource_change` / `scope_change` / `priority_change` / `abandon` / `early_completion` 之一 |
| 策略 | 必须是 `S0`–`S5` 之一，并说明为什么没用更轻的策略 |
| 被移动的任务 | 只列真正改了排期的任务；若移动了与变化无关的任务，注明原因 |
| 未受影响的任务 | 必填。这是对用户的承诺，也是下次重规划的基线 |
| 用户确认 | 涉及范围、截止、优先级变化时必须为「是」 |

**不记录**：日常勾选完成、无关紧要的微调、临时起意的想法。
